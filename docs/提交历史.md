## 二、阶段：输出上限体系（issue #71）

### 一、静态上限表

- **2026-09-29 17:24** — 新建 `scripts/sync-output-limits.mjs`，从 models.dev 生成 `MODEL_OUTPUT_TOKEN_LIMITS`，替换原先手工维护的单条记录。

## 三、阶段：Claude 缓存断点

### 一、问题定位

- **2026-09-29 17:41** — 用用户提供的 10 轮 `claude-sonnet-5-5` 计费日志反推，确认全程零缓存。
  - **怎么确认的**：按 Sonnet 5.5 公开价（input $2/M、output $10/M）逐条重算，10 条**全部吻合到分**，例如 `37898×$2/M + 1312×$10/M = $0.088916` 对上日志的 `$0.0889`。整段会话只要有一个 token 命中缓存读，总价就会偏离，所以这个吻合本身就是「零缓存」的证据，而不是某种显示问题。
  - **排除了误判**：`mapMessagesUsage()` 早就正确读取 `cache_read_input_tokens` / `cache_creation_input_tokens`，它如实上报了「请求所要求的一个零」。
  - **根因**：`buildMessagesBody()` 把 `system` 设成裸字符串，且 `tools`、`messages` 全部未标记。Anthropic 缓存按 block 显式开启，不标记即每轮按全额重算。全插件唯一的 `cache_control` 在 CLI 通道的 system 上（`cliSystem()`），而 Claude 家族根本不走 CLI。

### 二、断点位置取自官方客户端

- **2026-09-29 17:45** — 无额度可实测，改走上游构件取证，三份均校验 sha512 后再读。
  - **`command-code@1.68.0`**：唯一一处 `cache_control` 在 `toWireSystem()`；`provider/v1/messages` 在包内 0 次命中 —— 官方 CLI 从不走这个端点。
  - **`CommandCodeAI/pi-commandcode-provider`**（官方仓库）：用 Anthropic SDK 打同一端点，并从模型列表读 `pricing.cache_read` / `pricing.cache_write` 用于计费。
  - **`@earendil-works/pi-ai@0.87.1`**：其 `anthropic-messages` 传输自动标记**恰好三处** —— `system` 块、最后一个 tool（`compat.supportsCacheControlOnTools` 为真时）、最后一条 `user` 消息的最后一个 block；TTL 默认为空。
  - **为什么这样取证**：官方 provider 靠这个字段算自己的成本显示，网关若剥离，Pi 的会话成本会一直偏高并被用户发现。这比「网关大概会透传」强，但**仍不是实测**。

### 三、实现

- **2026-09-29 17:48** — `src/adapter.ts` 新增 `EPHEMERAL_CACHE_CONTROL`、`CACHEABLE_BLOCK_TYPES`、`markLastUserCacheControl()`；`buildMessagesBody()` 改为设置三个断点。
  - **为什么断点要落在最后一条 user 消息**：DSH 每轮重发完整历史，标在那里才是**滚动边界**；只标 system 的话，第一轮之后的历史仍全部重算，实测 input 成本约为三断点方案的两倍。
  - **约束**：`thinking` / `tool_use` block 不标记（下一轮即失效）；空 system 保持字段缺失而非发空 block；`messagesMessageCodec` 把工具结果也编码为 `role: 'user'`，工具循环的末轮同样能命中。
  - **不加 `ttl`**：默认 5 分钟足够推进中的会话，且 `ttl: "1h"` 的读/写价与之一致，只延长存活不降成本。
  - **不设开关**：网关若忽略该字段，形状与价格均与现状完全一致；认了但不命中也只贵首轮一次写入（$2.5/M 对 $2/M）。
  - **影响面**：`system` 在此通道变为单 block 数组（CLI 通道一直是这个形状，是字符串字段唯一能带标记的写法）；CLI 与 OpenAI 通道不动。
- **2026-09-29 17:50** — `tests/adapter.test.ts` 新增 4 个测试（tools 末项断点、最后一条 user 断点含工具循环、无 system/tools 时不误发、CLI/OpenAI 通道行为不变），并更新一处 `system` 断言。
  - **验证**：`npm run typecheck` 通过；`tests/adapter.test.ts` 226/226；`npm test` 742/742；`npm run build` 通过。
- **2026-09-29 17:54** — 同步 `CHANGELOG.md`、`docs/agent-reference/adapter-protocol.md`、`docs/issue-64-cache-review.md`。
  - **为什么写进 issue-64 文档**：那是本仓库唯一的缓存调查记录；本次故障与 #64 的 CLI 图片缓存退让是**相反的失效模式**，#64 的实验不可能发现它，必须写明这条界线，否则后人仍会以为已覆盖。

### 三、实现：孤立代理字符清洗

- **2026-09-30 00:01** — `src/adapter.ts` 新增 `LONE_SURROGATE_PATTERN`、`ANY_SURROGATE_PATTERN`、`sanitizeSurrogates()`，作为 `JSON.stringify` 的 replacer 接在**唯一的正文序列化点**上。
  - **为什么接在序列化点**：一处覆盖三个通道、所有字段（system、消息、工具 schema、工具结果），不必枚举「可能含文本的字段」而漏掉一个。
  - **先纠正自己的表述**：上一轮说「孤立代理字符会让 JSON 序列化直接炸掉」**不成立**。实测 `JSON.stringify` 会把它转义成 `"\ud83d"`，不抛错，字节层仍是合法 UTF-8。真实风险是**上游严格解码器**拒收，属推断而非已复现的崩溃。因此这是防御性改动，价值低于上一轮的表述。
  - **性能**：精确模式含 lookaround，V8 无法快速扫描。实测 412 KB 正文：单独用精确模式 1.40 ms，裸 `JSON.stringify` 0.59 ms。加一层无标志的范围预检后降到 0.77 ms。
  - **正则状态陷阱**：预检必须用**无 `g` 标志**的正则。带 `g` 的正则有状态，`test()` 会推进 `lastIndex`，导致同一字符串连续调用交替返回 true/false（已实测复现）。`replace()` 会自行重置，带 `g` 无妨。
  - **必须保留成对代理**：合法星平面字符（emoji）本身就是代理对，朴素范围过滤会删掉所有 emoji。
- **2026-09-30 00:02** — `tests/adapter.test.ts` 新增 2 个测试（三个通道的清洗、emoji 原样保留）。
  - **验证**：`tests/adapter.test.ts` 240/240，`npm test` 756/756，`npm run typecheck`、`npm run build` 均通过。

### 一、审查结论：核心声称成立

- **2026-09-30 00:14** — 审查 [PR #72](https://github.com/Mars-Sea/dsh-commandcode-provider/pull/72)（作者 cololi，6 个文件）。用 `dsh-release-upgrade` 技能收集上游 delta（基线 `dsh-v0.2.0-rc.1` = `4878cda`，目标 `dsh-v0.2.0-rc.2` = `639ed01`，1025 个改动路径、321 个包清单，收集脚本 `errors` 为空）。

## 十三、阶段：issue #73 压缩恢复分类修复（2026-09-30）

1. **2026-09-30**：会话贴近窗口上限时，`requestContextBudget()` 会把本次请求的输出预算压到 1,024 token 的应急地板；此前 `finish_reason=length` 且无正文/工具调用的空响应一律判为致命的 `OUTPUT_TOKEN_LIMIT`，不进重试白名单，导致长会话在死锁状态下反复失败、手动压缩也在同一状态下失败，唯一出口是切模型或新开会话（用户报告，issue #73）。
