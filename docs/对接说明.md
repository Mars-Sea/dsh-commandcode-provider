1. **准入声明为双通道区间（2026-10-28 扩展）。**`dsh.compatibility.dshReleases` 五条记录 `0.2.1-rc.2`、`0.2.1-rc.3`、`0.2.1-rc.4`、`0.2.1-rc.5` 与 `0.2.2-alpha.2`，`dsh.compatibility.dsh`、`engines.dsh` 与 34 个 `@deepseek-ai/dsh-*` peer／开发依赖同为 `>=0.2.1-rc.2 <0.2.2-0 || >=0.2.2-alpha.2 <0.2.3-0`。**为什么是两个分支**：`0.2.1` 的预发布序列是 `-rc.N`、`0.2.2` 的是 `-alpha.N`，一个区间表达不了；上界推到 `0.3.0-0` 会连两代之间的空档一起放行。每个分支上界带 `-0`，是因为按 semver 优先级 `0.2.2-rc.1 < 0.2.2`，写成 `<0.2.2` 会放行下一条版本线的 RC。`0.2.0-rc.2` 已退出 npm `latest` 并落在区间之外。宿主判定语义未变（自 `0.2.1-alpha.4` 起只读 `engines.dsh`，`semver.satisfies` 带 `includePrerelease: true`）。**`engines.node` 同时从 `>=22` 抬到 `>=24.9`**：`0.2.2-alpha.2` 自身声明 `engines.node >=24.9.0`，插件准入它就不能让整包下界低于该引擎能启动的水位；代价是 Node 22/23 用户失去支持，升级说明见两份 README 的独立小节。理由与代价见[《决策记录》第八章第17条](决策记录.md#八dsh-引擎兼容范围与验证边界)。
2. **Cordis 与 Schemastery 改为精确析取。**两代引擎的 vendor 配对不同（`0.2.1` 的 RC 配 `cordis 4.0.5`／`schemastery 3.18.5`，`0.2.2-alpha.2` 配 `4.0.6-alpha.1`／`3.18.6-alpha.1`），故写 `~4.0.5 || 4.0.6-alpha.1` / `~3.18.5 || 3.18.6-alpha.1`。**用精确版本而不是 `~4.0.6-alpha.1` 分支**：后者会放行 `4.0.6-alpha.2` 这类没有任何引擎配对的版本（node semver 实测：精确写法只接受两个实际配对版本）。这两个名字不匹配 `@deepseek-ai/dsh*` 前缀、宿主准入不读它们，差异只在 pnpm 解析层生效。
