# 决策记录

仅记录会影响后续实现的约束；接口细节以 `docs/agent-reference/` 和当前代码为准。

## 一、请求失败恢复

1. **2026-09-29 — 按故障证据分配重试预算。**`SERVER`、`TIMEOUT`、`EMPTY_RESPONSE` 和无明确额度窗口的 `THROTTLED`，每次模型请求最多自动重试 3 次；明确额度窗口的 `RATE_LIMIT` 保留等待恢复的能力；`TRANSPORT` 沿用独立预算。退避和服务商给出的等待时间继续交给 DSH 的 `dsh-llm-retry` 执行，插件只负责分类和次数上限。
2. **2026-09-29 — 一次模型请求的预算在 `step/start` 重置。**失败尝试产生的 `assistant/attempt` 不能重置预算；取消请求不消耗预算。预算耗尽后结束当前请求并给出中文诊断。
3. **2026-09-29 — 跨请求存活的故障状态必须按会话隔离，而不是挂在适配器单例上。**`CommandCodeAdapter` 全进程只 `new` 一次并共享给所有并发 agent；`headerTimeoutStreak`（连续 header 超时计数，用于在 `TIMEOUT` 白名单重试之外额外升级为终态诊断）曾是该单例上的普通字段，导致并发会话互相清空或污染彼此的计数，升级诊断在并发下基本失效。**约束**：该类状态若要跨 `stream()` 调用存活（这里是 dsh-llm-retry 的重试机制决定的，不能收窄到单次调用内），必须按 `GenerateOptions.sessionId` 隔离（不是 `agent`：`GenerateOptions` 未携带 agent 引用），并对字符串 key 的 Map 做界的容量上限 + 先进先出淘汰（不能像 `WeakMap<agent,…>` 那样自动回收）；无 `sessionId` 的一次性调用退回旧的单槽全局行为。同类新增状态照此模式，不要再挂实例字段。
4. **2026-09-30 — 贴边预算/失败分类要按“预算是否真被地板钳死”判断，不能只用粗粒度的“存在尺寸压力”。**`requestContextBudget()` 的 `sizePressure` 为真时，本次请求的输出预算不一定真被压到 `MIN_CONTEXT_OUTPUT_TOKENS`（1,024）那条应急地板，可能只是比请求值小、但仍远高于地板；此时的 `length` 截断是正常的话痨截断，不是窗口超限。issue #73 里塌地板导致的 `length` 空响应误判为致命 `OUTPUT_TOKEN_LIMIT`、会话死锁，若直接照搬 issue 原文建议用 `sizePressure` 改判 `CONTEXT_WINDOW_EXCEEDED`，会把前一种正常情况也误判为窗口超限，触发不必要的有损压缩。**约束**：新增了更精确的 `RequestContextBudget.floored` 信号（`available <= floor`），只有 `floored` 为真才改判 `CONTEXT_WINDOW_EXCEEDED` 触发压缩重试；`sizePressure` 继续只用于它原本覆盖的场景（HTTP 400 的模糊网关拒绝分类）。同时不做“预算已知会塌到地板就提前于发送前失败”这类拦截——1,024 tokens 是否“注定空响应”取决于具体模型/思考强度，不是可以提前断言的普适规律，提前拦截的误伤成本高于放行一次注定失败的计费请求。同类“贴边预算/失败分类”判断照此粒度取舍。**已被下条决策取代（2026-09-30，issue #74）：`requestContextBudget()` 连同本条的 `floored`/`sizePressure` 分类整体移除，本条只作为历史记录保留。**
6. **2026-09-30 — 展示"当前激活账号"的代码路径必须和真实请求路由共用同一套探测复活逻辑，不能各写一份。**
   issue #51 反馈者的后续截图显示：设置页账号卡片和侧边栏统计会"切到另一个账号"，且比实际对话恢复得慢。
   根因是 `src/index.ts` 的 `usageReports()` 直接调用裸 `selectActiveAccount()`（纯同步过滤，不探测），
   而 `resolveKey()`（真实请求路径）对显式选中账号有专门的探测复活机制——两条路径各写一份"当前该用谁"，
   必然会因为其中一份缺了后来加的能力而不同步。**约束**：把 `resolveKey()` 内联的"显式账号回退前探测复
   活"与"全员标记时批量探测"两段逻辑抽成 `CommandCodeAccountPool` 的私有方法（`reviveExplicit()` /
   `probeAllMarked()`），新增公开方法 `activeAccount()` 复用它们，供展示场景调用；`resolveKey()` 本身只
   做了纯重构，行为不变（54 条既有账号测试全过）。之后任何"哪个账号在用/该显示成用哪个"的新判断逻辑，
   只能加在这两个共享方法或 `selectActiveAccount()` 里，不能在展示层单独另写一份。`activeAccount()` 与
   `resolveKey()` 的有意差异：不消耗 `tried`、不做模型路由、全员不可用时返回 `undefined` 而不抛错。
   反馈里"选了还有额度的账号却被切到没余额账号导致会话中断"这一半未处理，需要真实零余额账号复现后再判断
   是分类覆盖面问题还是"流中途拒绝不轮转"的既有设计取舍。
7. **2026-09-30 — 撤销客户端预判收紧 `max_tokens` 的整套机制（`requestContextBudget()`），改为完全依赖上游自身的超窗口拒绝 + 既有的 `isContextOverflowDetail` 分类恢复（issue #74）。** issue #74 反映"长对话输出被硬切"：根因定位到 `requestContextBudget()`——随对话变长，估算输入占用增大，会把本次请求实际发送的 `max_tokens` 动态压低，副作用正是"对话越长、输出越容易提前被截断"。该函数本身是 issue #67 的验证过的修复（`docs/issue-67-empty-response-review.md`）：未收紧时，固定 `max_tokens` 的请求一旦連同提示词超出模型窗口，上游曾经会返回**模糊的** `400 "The stealth model could not complete the request."`，不带窗口字样，导致回合直接失败且不会触发压缩重试。是否要为了解决 #74 的"误伤长对话正常输出"而重新引入 #67 的"超窗口请求死路"风险，不能凭猜测决定。**验证**：用户要求实测而非直接采纳/拒绝。2026-09-30 用免费模型做了两组 A/B：① `stealth/pixel-canary`（262K 窗口，issue #67 当年测出模糊 400 的那个模型）当时持续 503／404，模型自身不可用，无法直接复现；② `stealth/space-bunny-alpha`（免费，1,000,000 窗口）构造约 453 万字符提示词（估算约 113 万 token）+ 固定 `max_tokens: 64000`，超窗口约 19.6%（与 #67 当年模糊 400 案例的超额比例相当）、且完全跳过 `requestContextBudget()`（不预热目录，`contextWindow` 恒为 `undefined`，函数早退不做任何收紧）：**上游直接返回清晰的 `400 the request exceeds the model's context window`**，被既有、独立于 `requestContextBudget()` 的 `isContextOverflowDetail()` 正确分类为 `CONTEXT_WINDOW_EXCEEDED`，走压缩重试，没有出现模糊 400。**约束**：接受"pixel-canary 这一具体案例今天无法直接复测"这个已知空白，采信 space-bunny-alpha 的证据，完全移除 `requestContextBudget()`、`estimateWireInputTokens()`、`RequestContextBudget.floored`/`sizePressure`，以及 `emptyCompletionError()`/`generateHttpError()` 里依赖它们的两条改判分支（连同上条 issue #73 的 `floored` 判据、`generateHttpError()` 的模糊 400 sizePressure 分支一并回退）。`max_tokens` 恢复为只按模型自身输出上限（目录 + 运行时学习到的上限）与网关总上限 `DEFAULT_GENERATE_MAX_TOKENS`（131,072）计算，不再按单次请求的提示词大小动态收紧；真正的超窗口请求完全依赖上游自身拒绝 + `generateHttpError()`/`streamErrorToLlmError()` 已有的 `isContextOverflowDetail` 分类恢复。若后续在其他模型上重新观察到模糊 400（不带窗口字样、回合直接失败且不进压缩重试），需要重新评估是否要恢复某种形式的客户端预判。
8. **2026-10-14 — 只有 Messages 端点的权限拒绝才追加 CLI 直连回退，边界锁死在 HTTP 403 加结构化 `permission_error`（issue #84）。** 反代转发 Claude 的那条链路可能单独对某个账号失效，而同一把密钥的 CLI（命令行协议）直连 `/alpha/generate` 仍可用，因此回退触发面从"仅 `upgrade_required`（套餐升级门槛）"扩为"`upgrade_required` 或 Messages 的 `permission_error`（权限错误）"。**约束**：判定只看 HTTP 403 且解析出的 `code`/`type` 恰为 `permission_error`，不扫原始正文——否则整页 HTML 错误或回显消息都能换来一次传输切换；`MODEL_NOT_IN_PLAN` 等其它权限失败保持原样上报且不重试。该回退与既有 Messages 降级一样不写 `protocolCache`：缓存按网关与密钥索引，而路由还取决于模型，记住它会把整个账号的其它模型拖离 Provider API（第三章第1条）。账号轮换时清空"此前 Messages 拒绝"的注记，它只属于刚被换下的那把密钥；回退后 CLI 也失败时，错误文案以 CLI 那次结果为主句并附先前的 Messages 标识，两个失败正文都不回显。**证据边界**：核查日在本机 GOAT（`individual-goat`）账号实测反代与 CLI 两条路都返回 200，报告者的 `permission_error` 未能复现；触发分支由合成用例覆盖，回退出口用真实服务端端到端验证（合成 403 后 `/alpha/generate` 返回 200 并正常收流）。后续不得因"本机未复现"删除这条回退，也不得把触发面扩大到其它状态码或错误标识。

9. **2026-10-17 — 新增 `maxOutputTokens`：一个数值字段表达「沿用推导／只收紧／不发送」三态（问题 #74）。**#74 报告者要的是"输出不再被硬切"，而 `max_tokens` 是被动的硬限制——调大数值只是把断点后移，并不解除它，所以本轮给的是"可以不发这个字段"的开关。**三态语义**：未设置＝沿用既有推导（模型公布或运行时学到的输出上限、网关总上限三者取最小，既有配置行为不变）；正整数＝与推导值取最小，**只收紧不放大**，越界值由配置校验拒绝；`0`＝请求中**不发送** `max_tokens`，把单轮输出规模交回平台。`0` 不是"很小的预算"而是指令，因此它同时是字段下界（`OMIT_OUTPUT_TOKENS`）：`applyMaxOutputTokens()` 对它原样返回推导值，trace 记录、降档恢复与 `OUTPUT_TOKEN_LIMIT` 诊断读到的仍是真实数值（不会报成 `max_tokens=0`）。**省略受两条守卫约束**，少任何一条都会把开关变成故障：(1) Anthropic Messages 端点必填该字段，缺失会被上游以 `Invalid input: expected number, received undefined at max_tokens` 拒绝，故 `omitOutputTokens()` 对 `messages` 恒为 false，Claude 链路继续按推导值发送；判定按**每次构建正文的目标协议**做，因为协议回退会换传输。(2) 宿主显式传入的每次调用预算（`GenerateOptions.maxTokens`，如会话标题的 64 词元）是指令而非默认值，同样使省略为 false，否则会解除 #88 所依赖的那道边界。**约束**：规则单点持有在纯模块 `src/output-budget.ts`（`applyMaxOutputTokens`／`omitOutputTokens`／`MAX_OUTPUT_TOKEN_LIMIT`，无 node 内建导入，设置页直接打包导入同一常量），`DEFAULT_GENERATE_MAX_TOKENS` 只是该常量的历史别名；正文构建后只剩**一处** `max_tokens` 重写（每次连接前按本次学习上限收紧，`assignMaxTokens()` 全仓唯一调用点），它同样先问 `omitOutputTokens`，否则会把已省略的字段重新写回去，413 降档只降图片预算、不重写该字段。同期把 Host 侧 7 个调用点（用量查询、`/commandcode` 命令、账号卡片用量、登录流程、终端设置页注册、网页搜索的请求与凭据解析六类）与浏览器侧 6 个调用点（分布在 5 个文件）的裸 `error instanceof Error ? error.message : String(error)` 收口到 `src/readable-error.ts` 的 `readableErrorText()`：跨 webview／host 边界被结构化克隆的非 `Error` 抛出此前会退化成 `[object Object]`。页面侧字段语义见[《客户端与设置》](agent-reference/client-and-settings.md)，wire 侧见[《适配器协议》](agent-reference/adapter-protocol.md)。**验证**：本地 `npm run typecheck` 干净、`npm test` 1027 项全过、`git diff --exit-code -- lib/` 为空（本次修复后）。CI run 38845201129（head `23f3a4e`）上 `npm run typecheck`、`npm test`、`npm run build` 均通过，`git diff --exit-code -- lib/` 失败——提交进仓库的 sourcemap 保留了作者 Windows 工作树的 CRLF（`lib/index.js.map` 13753 处、`lib/client.js.map` 11488 处 `\r\n` 转义），ubuntu runner 检出 LF 源码后重建即产生差异；该污染已在本次修复中于 LF 环境重建归一，两个 `.map` 的 `mappings`／`sources`／`names` 与功能产物 `lib/*.js`、`lib/index.d.ts` 均逐字节不变。**边界**：`0` 对 Claude 系无效是上游契约决定的，不是本插件的取舍；TUI 设置页未接入该字段（与 #86 的 `contextWindow` 先例一致），目前只有 Web 设置页可改。

## 二、标准协议复用边界

1. **2026-09-29 — 复用 DSH 的通用能力。**重试退避、会话步骤、压缩恢复、图片附件服务和模型请求接口由 DSH 负责；本插件不另建通用重试调度器或附件存储。
2. **2026-09-29 — 保留 Command Code 的网关适配。**`/alpha/generate`、`/provider/v1/chat/completions` 和 `/provider/v1/messages` 的请求体、流事件、账号套餐与轮换、模型目录路由及上游错误证据并不共用一种传输契约。插件只维护这些网关特有的转换与选择逻辑；新增通用能力时优先查 DSH 官方接口，再决定是否需要本地实现。
3. **2026-09-30 — `/alpha/generate` 补发 `permissionMode:"standard"`、`x-taste-learning` 改为 `"false"`；均为协议对齐，不是 issue #64 的修复。**对照官方最新 CLI（1.72.4）源码，发现请求体还有 `permissionMode`/`mode` 两个我们从未发送的顶层字段。免费模型真实探测确认：两者缺省时服务端有枚举校验但不报 400，多次重复对照（`max_tokens` 放宽到 200 后）未观测到响应结构差异，第一轮"缺 `permissionMode` 就只有推理没有文本"的结果是 `max_tokens:16` 太小导致的随机噪音，已证伪。但 `toWirePermissionMode()` 会把内部默认值 `"default"` 归一化为线上值 `"standard"`，与 `docs/issue-64-cache-review.md` 上游证据表已记录的结论一致，因此补发 `"standard"`。**约束**：该文档"root-cause boundary" 一节已经测过这个值对 CLI 传输的图片缓存回退问题没有修复效果，后续排查 #64 不要重复归因到这里。`mode` 字段的合法枚举已探测到，但一次普通会话该传什么值未从静态代码定位到，仍是已知但无害的缺口，未处理。`x-taste-learning` 由 `"true"` 改为 `"false"`，依据是第三方实现（magpie）的观察值，未做进一步实测验证是否有实际影响。

4. **2026-10-15 — 会话标题仅在模型明确支持时自动关闭思考（问题 #88）。**`purpose: 'session-title'`（会话标题用途）优先使用模型已声明的 `off`（关闭思考），避免默认 64 词元预算被思考耗尽；两种聊天协议及内部回退使用同一选择，保留输出预算且不改写调用选项。普通对话、`compaction`（上下文压缩）、未声明关闭思考能力及未知模型沿用原策略，不以小输出预算推断用途，也不向 Messages（消息接口）发送不支持的值。既有纯思考超限诊断和重试分类保持不变。适配器回归及真实宿主运行时使用合成响应验证，不能据此宣称真实提供商标题质量已验收。

## 三、网关状态隔离

1. **2026-09-29 — 按接口基址隔离缓存。**运行时学到及目录公布的模型输出上限按 `apiBase` 与模型共同索引；套餐和协议选择按 `apiBase` 与账号密钥共同索引。同名模型、相同密钥在不同网关下不共享结论。
2. **2026-09-29 — 磁盘目录须带来源。**目录缓存版本升为 3 并记录 `apiBase`。旧格式或来源不同的文件无法证明属于当前网关，离线时不采信；成功刷新后自动写入新格式。

3. **2026-10-02 — 单次调用固定请求事实。**调用开始固定连接与账号定义，取得对应来源目录后固定路由及公布能力；内部账号轮换、协议回退和唯一降档沿用原事实，新调用使用新配置。明确上游拒绝仍触发既有回退与学习。
4. **2026-10-02 — 并发已有较低学习值不吞降档机会。**本次收到有效输出上限拒绝后，以实际发送预算判断能否降低，使用本次拒绝与同网关同模型已学值中的较小值；共享学习是否发生更新不能决定本次是否重试。仍须尚未交付任何块且唯一机会未使用。
5. **2026-10-02 — 账号健康与探测按网关隔离。**同网关同密钥共享限流、禁用及显式探测节流，不同网关分别记录；旧请求及迟到探测结果只作用原网关。请求与用量展示共用既有恢复规则，报告在恢复后读取健康事实，遵守第一章第6条。
6. **2026-10-02 — 本次固定账号定义，引用秘密实时解析。**账号列表、固定账号及模型规则在调用开始固定；每次账号选择重新解析引用凭据及默认授权文件，保留既有优先级与兜底。替换或清除可影响后续选择，但不撤回已发请求及当前尝试已取得的密钥；配置中的直接密钥随定义固定。
7. **2026-10-02 — 每次连接前仅采纳更低学习值。**账号尝试、协议回退和降档发出前读取同网关同模型的更低已学上限；目录刷新不能放宽本次预算，也不增加重试次数。本条不恢复第一章第7条撤销的提示词大小预算。
8. **2026-10-02 — 最新发起刷新接管共享发布权。**同网关跨实例、跨缓存路径的刷新按发起顺序接管共享事实发布权；旧结果仍供原等待者使用，但不能倒灌共享上限。解析先完整校验再发布，失败或无有效模型保留旧有效事实；有效新目录可移除此前公布字段。磁盘兜底不得覆盖较新联网事实，生成冷读取不额外联网。

## 四、账号开通过程

## 七、上游快照同步边界

1. **2026-10-03 — `off` 按快照透传，不做统一丢弃。**`off` 有两义：宿主用它表示"未请求思考强度"，而官方自 command-code@1.73.3 起把 `off` 作为 DeepSeek V4 系列的真实档位。判定只看快照——`KNOWN_EFFORTS[model]` 列出 `off` 才原样下发，未列出的（Claude 全系，以及始终三档的 `deepseek-v4-flash-fast`）继续丢弃。**依据**：官方 CLI 的请求体只要 effort（思考强度）是非空字符串就原样下发，所以关停思考靠的是 `reasoning_effort:"off"` 这个字段本身，省略字段反而关不掉；反之 Messages（消息）传输的 `output_config.effort` 没有 `none` 值，必须不发。**实测（2026-10-03，`deepseek/deepseek-v4-pro`）**：不传 effort 仍产生 156 个推理 token（证明省略字段不是关闭方式），`high` 147 个，`off` 0 个；对照未列出 `off` 的 `deepseek-v4-flash-fast`，传 `off` 时不发字段、仍产生 193 个推理 token。今后上游再给某族新增"可关思考"档位时沿用本条，不另立规则。
